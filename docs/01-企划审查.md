## §2 技术问题清单

### P0 —— 会直接返工的问题

**2.1 企划 3.2 的「ADB 路径 B」在本项目里不成立。**
企划写：移动端用 Shizuku 或自实现 ADB 协议连本机 adbd，然后 `input` 命令注入事件。问题：

- `adb shell input` 只能发 `keyevent` / `tap` / `swipe` / `text`，**无法产生模拟摇杆轴、模拟扳机、模拟多键同时按下**，也无法让 PC 侧游戏收到手柄输入。它跟"虚拟手柄"是两条路。
- Shizuku 提供的是"以 shell 身份调用系统 API"的能力，**不提供 `input` 注入通道**，企划把它当注入方案是错配。
- adbd 本身需要 root 或无线调试配对，权限成本远高于收益。

**结论**：路径 B 应当删除。若原意是"手机游戏自控"（用虚拟手柄 UI 控制**手机自己**在跑的游戏），那是另一个产品，虚拟手柄类型（DS4/Xbox）也无意义——需要你确认需求边界，见 `docs/03` 决策 D1。

**2.2 ADB 端口转发方向写反了。**
企划：「PC 端通过 adb 将 Android 设备端口转发到 PC」。
正确做法是 **`adb reverse tcp:PC侧端口 tcp:手机侧端口`**（reverse = "把 PC 的端口映射到设备上"）：手机 App 在本地 `127.0.0.1:8080` 起 TCP server，PC 执行 `adb reverse tcp:8080 tcp:8080`，之后 PC 连 `localhost:8080` 即等于连到手机。`adb forward` 是相反方向（PC 端口 → 设备），用在这里连不上。这个细节写错会让实现阶段白调半天。

**2.3 缺"通信中断保护"（fail-safe）。**
虚拟手柄最典型的线上事故：WiFi 抖一下连接断了，PC 端最后一帧是"前进键按下"，角色原地狂奔到撞墙。**协议必须定义超时（建议 200–500ms 未收到心跳即视为断开）并强制归零所有轴/松开所有键**。企划通篇没提。

### P1 —— 影响手感与架构

**2.4 只单向设计了。** 震动反馈（PC → 手机）、延迟测量、连接状态都要求反向通道。企划把它放在 4.3 当作"如果移动端支持"的可选项，实际它是**架构决策**：要么 UDP 双向，要么 UDP 数据 + TCP 控制通道。一开始不设计，后面要动协议。

**2.5 发送节拍没定。** 企划把"触摸事件 → 数据包"隐含成一比一。正确链路是：触摸采样（屏幕 60–120Hz）→ 归一化/死区/圆形裁剪 → **固定节拍（60Hz 或 120Hz）打包全量状态快照** → 发送。固定节拍 + 全量快照的好处是**丢包无害**（下一帧自然覆盖），这也正是 UDP 可行的原因。企划选了正确的传输方式，但没写清这条约束，容易被实现成"事件增量包"，那样一丢包就永久错位。

**2.6 ADB/TCP 模式下没提 `TCP_NODELAY`。** 不关 Nagle，小包会被攒到 ~40ms 才发，手感直接完蛋。

**2.7 WiFi 下的网络安全没提。** 局域网里任何人都能连上你的 PC 服务并注入输入。至少要有配对码/预共享令牌。VIIPER 的做法可参考（ChaCha20-Poly1305 认证）。

**2.8 "DS4 是卖点"需要打折。** 绝大多数游戏只认 XInput；虚拟 DS4 的实际价值主要是**让游戏显示 PlayStation 按键图标**，而且它要跟 Steam Input 打架（Steam 默认开启 Xbox 配置支持，会把检测到的手柄再映射一遍 → 双输入/按键跳两格）。合理定位是：**Xbox 360 (XInput) 为默认，DS4 为可选**。另外虚拟设备是 DInput/HID 设备，**带反作弊的联机游戏不保证可用**，这条要写进 README 避免用户预期落空。

**2.9 内核驱动 vs 用户态。** ViGEmBus 是内核驱动，安装要管理员 + 签名 + 反作弊对抗；VIIPER/HIDMaestro 走用户态（USBIP / VHF），这已成为业界迁移方向。选型时这是加分项。

### P2 —— 补充项

- **2.10** XInput 只有 4 个槽位，且游戏可能"占槽不放"，多手柄要做好槽位管理。
- **2.11** UDP 广播/mDNS 自动发现：Windows 防火墙首次会拦截，需要可操作的提示（或让用户手输 IP 兜底）。
- **2.12** 移动端工程细节企划没提：锁横屏、沉浸式全屏、屏幕常亮、摇杆的可视化反馈与死区校准、多点触控手势冲突。
- **2.13** 二进制协议 vs JSON：JSON 在这个带宽下完全够用（60Hz × 数百字节 = 几十 KB/s），企划判断正确；但**建议协议里带 `seq` 序号**以便统计丢包率（企划 3.4 想要"显示丢包率"，没有序号就统计不出来）。

## §3 企划没写、但开工前必须有答案的（已定，结论见 `docs/03` §1）

1. **产品边界** → ✅ ADB = 手机↔PC 的 USB 数据传输通道；虚拟手柄统一在 PC 侧创建（D1）。

4. **虚拟手柄后端** → ✅ 先 ViGEmBus，抽象层预留 VIIPER（D4）。
5. **移动端技术栈** → ✅ Kotlin + Android Studio 原生 + Material 3（D5）。
6. **"根本不装 PC 端软件"的路线** → ⏳ 蓝牙 HID 直连列为 P5 之后的可选模式（D2，待定）。

## §4 对企划的正确部分，予以保留

- 三件套分层（移动端采集 / 核心通信层 / PC 端虚拟手柄）是对的。
- 协议用**全量状态快照**、字段里显式带 `controller` 类型、扳机用 0.0–1.0 浮点——都对。
- WiFi 用 UDP、ADB 用 TCP——都对（补 §2.6 的 NODELAY）。
- UI 从"手柄类型"反推布局模板（Xbox 的 A/B/X/Y ↔ DS4 的 ✕/○/△/□）——对。
- 自动发现、配置保存、连接状态显示——对。
- 先 fork 一个现成项目而非从零写——策略对，但**选的树不对**（`docs/02` §2 给了替代建议）。
