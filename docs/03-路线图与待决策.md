### D4 为什么这么选（大白话）

- **ViGEmBus**：在你的 Windows 里装一个驱动，装完之后你的程序就能"凭空造出一个手柄"，游戏以为你插了个真的 Xbox 手柄。**装一次、要管理员权限、之后随便用**。代码量最少，出问题网上能搜到答案，三天能出结果。缺点：原作者 2023 年因商标纠纷停更了，软件冻结不动（但全世界大量软件至今仍在用它，稳定是验证过的）。
- **VIIPER**：更新的做法，支持的机型更多（含 PS5 手柄），也不用改系统内核。但 Windows 上要额外装一个 USB-over-IP 的驱动，链路更长、环节更多、中文资料几乎没有——现阶段会把调试时间全吃掉。
- **结论**：先用 ViGEmBus 拿到"能玩"的状态；在代码里留一个**插座**（接口），将来真需要 VIIPER 时换插头即可，不用重写。

> 环境里的其它语言怎么用：**Go**——写协议压测器/发包器（模拟 4 个"假手机"狂发 UDP，验证 PC 端稳定性和 fail-safe）；**Python**——调研脚本、快速验证（Joy2DroidX 服务端就是 Python，可以直接跑起来对照握手行为）；**JS**——本方案不用（Electron 的延迟和体积在低延迟输入场景不划算）。

**P0 额外发现（已成为决策依据）**：

- **BuanaVPad 的移动端是 Flutter**（不是原生 Android），PC 端是 **Python**——企划完全没提。它作为"参考"的价值大于作为"主干"。
- **Joy2DroidX 用 Socket.IO 事件式增量协议**（走 TCP/WebSocket，有队头阻塞）。这正好反证了 PadLink 选"UDP + 固定节拍全量快照"的理由。
- **VIIPER 与 Joy2DroidX 都是 GPL-3.0**：接入 VIIPER 必须走"独立进程 + TCP API"，不能链接它的库，否则 PadLink 也得 GPL（见 `docs/02` §3）。
- 本机 `JAVA_HOME` 是 JDK 17（AGP 8.5.2 的下限）。**JDK 25 会破坏 Kotlin 编译器**，构建 Android 端必须用 17。

### P2 · ADB 模式（预计 1 周）⭐ 优先于 WiFi

> **为什么排到 WiFi 前面**：用户的原话是"我屋网不好，想用 ADB 但没有"。
> 他现有的软件 EMotion（PC 端 `D:\Emotion`，C# + `Nefarius.ViGEm.Client`）**只有 WiFi，没有 ADB** —— 这正是 PadLink 存在的理由。
> 所以 ADB 不是"以后再说"，而是**第一条要打通、也是唯一必须打通的路径**。

前置风险已验证（2026-10-04）：`adb reverse` 隧道成立，见 `protocol/protocol.md` §1.1 的实测记录与 `tools/adb_tcp_probe.py`。

- [x] **ViGEmBus 后端**（`PadLink.Backends.ViGEm`，`Nefarius.ViGEm.Client` 1.21.256）—— Xbox 360 + DS4 两种设备
- [x] 映射自动验证 `--verify`：创建真手柄 → 提交状态 → **XInput 回读比对**，12 项全过
- [x] 端到端验证 `--probe`：Python 假手机 → 服务端 → ViGEmBus → XInput 里读到 A 键 0x1000 + 摇杆 32767
- [x] 空闲会话回收（默认 5 分钟无数据 → 销毁虚拟手柄；`--idle-seconds` 可调，已实测）
- [x] **PC 端管理界面**（`PadLink.Gui`，WinForms）：启动/停止、会话表格（地址/手柄/玩家/收帧/丢包/空闲/状态）、实时日志
- [x] 服务端抽成 `PadLinkHost`，CLI 与 GUI 共用同一套逻辑
- [x] 会话按 **player** 索引：手机重连换源端口时复用同一虚拟手柄（修复前每次重连都新建设备，会占满 XInput 槽位）
- [x] **PC 端 TCP 输入通道（ADB 模式）**：一条连接上按首字节切分二进制帧与 JSON 控制消息，握手 `hello→welcome→start→started`
- [x] **adb reverse 自动管理**：自动找 adb、列设备、建/拆隧道（CLI 的 `--adb`，或 GUI 的「ADB 连接」按钮）
- [x] GUI 点关闭缩到**系统托盘**，托盘右键 {打开} / {退出}，双击托盘恢复
- [ ] 移动端**最小手柄 UI**（Material 3，不用 VirtualGamePad 那套）
- [ ] 移动端 TCP **client** 连 `127.0.0.1:42312`，`TCP_NODELAY` + 固定节拍发送
- [ ] 无线调试（Android 11+）：`adb pair` / `adb connect` 引导
- [ ] 连接模式 UI（ADB / WiFi）

**已验收（PC 端完整）**：`--verify` 12 项全过；GUI 起来后假手机一发数据，界面上就能看到会话、帧数、丢包、归零状态。

**尚未验收**：手机真机接管 —— 卡在两个地方，一是移动端 UI 还没做，二是 ADB 的 TCP 数据通道（协议 §1.1）还没实现。
