# 02 · 技术路线

前置：`docs/01-企划审查.md`。本文给出建议方案，标 ⭐ 的是需要你拍板的点（见 `docs/03`）。

---

## §1 先回答：要不要做"手机当蓝牙 HID 手柄"这条线

企划默认了"必须有 PC 端软件"。但 Android 10+ 有 `BluetoothHidDevice` profile，**手机可以直接把自己注册成一台蓝牙 HID 手柄**，PC 端零软件、零驱动、零管理员权限、无关局域网、无关反作弊。

| | 蓝牙 HID 直连 | WiFi（本题路线） | ADB |
|---|---|---|---|
| PC 端安装 | **无** | 需装服务 + 驱动 | 需装服务 + 驱动 + adb |
| 配网要求 | 无 | 同一局域网 | 无 |
| 延迟 | 10–30ms | 2–8ms（5GHz 同房） | 3–10ms（USB 隧道） |
| 震动回传 | 受限（依赖 output report，Android 暴露有限） | 完整 | 完整 |
| 自定义布局/宏 | 可以，但纯本地 | 可以，且能存 PC 端 | 同 WiFi |
| 设备类型 | 你写 HID report descriptor，能扮成任意手柄 | 由 PC 端后端决定 | 同 WiFi |

**建议**：不把 BT HID 当作替代，而是当作**同一个 App 的第三种传输模式**（`BT_HID` / `WIFI` / `ADB`）。它是"我想立刻用，别让我装东西"的答案，也是竞品（Magic Gamepad、Bluke）在做的事。⭐ D2

## §2 起点：fork 哪棵树

企划选 BuanaVPad 作主干。重新评估：

| 候选 | 语言/栈 | 许可 | 状态 | 作为起点的评价 |
|---|---|---|---|---|
| `isaui/buana-vpad` | Android + Windows | MIT | ~18★，2025-04 后未动 | **可作 UI/布局编辑器的参考**，代码量小、许可干净；但一年多没维护，别指望它跟上游同步 |
| `OzymandiasTheGreat/Joy2DroidX{,-server}` | Android(NativeScript) + **Python** | 见仓库 LICENSE | 2024-07 归档 | **映射逻辑的最佳参考**：唯一同时实现 Xbox 360 + DS4 的现成实现，且服务端是 Python（可读性高、你能直接跑起来对照握手流程） |
| `experiment322/controlloid-*` | **React Native** + C | **GPL-3.0-only** | F-Droid 在架 | 布局编辑器成熟，但 RN 的触摸延迟在虚拟手柄场景是硬伤，且 **GPL 传染** |
| `Alia5/VIIPER` | C/C++ 服务端，含 C# 客户端 | 开源 | **活跃** | 不是"App"，是**虚拟手柄后端**，可直接当依赖用 |
| `hifihedgehog/PadForge` | C#/.NET 10 | 开源 | 活跃 | 太重（完整 remapper），但它的驱动层与设备模型值得读 |

**建议（⭐ D3）**：

- **不从零写，也不整树 fork**。走"**参考实现 + 自研主干**"：
  - 你的项目真正的核心是**协议 + 设备无关输入模型**，这部分任何现有项目都没做好（Joy2DroidX 有雏形，但绑死在 Python/ViGEm 上）。
  - 直接抄架构、抄布局编辑器交互（BuanaVPad MIT，可自由借鉴代码）、抄 Xbox/DS4 映射表（Joy2DroidX，先核 LICENSE）。
  - 开局把 `docs/protocol.md` 写死，两端各自独立开发、用同一份协议测试向量对齐。

理由：这些项目都绑在 ViGEmBus 上（已停更），整树 fork 等于继承一个停更依赖 + 别人的历史包袱；而它们加起来也就万行级别，改造它们的成本不比自研低。

## §3 PC 端虚拟手柄后端 ⭐ D4

| 方案 | 形态 | 可模拟设备 | 维护 | 许可 | 评价 |
|---|---|---|---|---|---|
| **ViGEmBus + `Nefarius.ViGEm.Client`** | 内核驱动 + .NET 库（NuGet） | Xbox 360, DS4 | **EOL 2023-11** | BSD-3 / MIT | 集成成本最低、资料最多、C# 一等公民。代价：冻版 + 更新器域名隐患需处理 |
| **VIIPER**（Alia5） | 用户态 + USBIP（Win 需 `usbip-win2`） | X360, DS4, DualSense, Switch2 Pro | 活跃 | 开源 | 被 HandheldCompanion 采纳；有 C# 示例与 TCP API；天然跨平台，为将来 Linux 留路 |
| **HIDMaestro** | 用户态 DLL | 多种（宣称 drop-in 替代） | 活跃 | MIT | 免 EV 证书、免内核驱动，吸引力大；**一手资料未核实**，风险中等 |
| vJoy | 内核驱动 | 通用 DInput | 半死 | 宽松 | 不产生 XInput/DS4 身份，不满足需求 |

**建议**：定义 `IVirtualControllerBackend`（Create/Submit/Dispose，输入用中立 `GamepadState`），**先把 ViGEmBus 后端打通拿到可用性**（因为它最快出结果），**同时把 VIIPER 列为 v0.3 的第二后端**，用抽象层隔开。不要一上来就上 VIIPER——USBIP 那条链路（装驱动、枚举、槽位）的调试成本远高于 ViGEm。

无论选哪个，README 必须写明：
1. 需要装驱动（管理员一次）；
2. **不保证在带反作弊的联机游戏里可用**；
3. 若用 ViGEmBus，附带更新器域名处理说明。

## §4 移动端技术栈 ⭐ D5

| 方案 | 优势 | 风险 |
|---|---|---|
| **Kotlin + Jetpack Compose + Canvas 自绘** | 触摸事件延迟最低（直通 `MotionEvent`）、可精确控制渲染、Android Studio 原生调试、`BluetoothHidDevice` API 直用 | 与 PC 端两套语言 |
| **.NET MAUI** | 与 PC 端同一语言/C#、可共享协议模型代码 | 虚拟手柄几乎全是自绘控件，MAUI 控件体系帮不上忙；`GraphicsView`/自定义绘制的帧率与触摸延迟在低延迟场景属**未验证风险**；仍要装 Android SDK；`BluetoothHidDevice` 要走 Android 绑定层 |
| React Native（复用 Controlloid） | — | 触摸延迟最差，且 GPL |
| NativeScript（复用 Joy2DroidX） | — | 项目已归档，作者自称"需要完全重写" |

**建议**：**移动端 Kotlin 原生 + PC 端 C#**。两端的耦合面只有协议一层，共享语言的收益很小，而触摸延迟是这个产品的核心指标。如果 C# 单语言的优先级高于手感，MAUI 也可行，但要接受先在真机上做**触摸延迟与帧率基准测试**再决定（可作为一个 spike，见 `docs/03`）。

## §5 架构

```
┌── Android ──────────────────┐              ┌── PC (Windows) ─────────────────┐
│ ① 输入模型 InputState        │              │ ④ 会话管理 SessionManager       │
│   （设备无关，两端同构）     │   WiFi/UDP   │ ⑤ 协议编解码 Codec              │
│ ② 布局渲染（自绘控件）       │◄════════════►│ ⑥ 输入映射 Mapper               │
│ ③ 传输 Transport             │   ADB/TCP    │   （InputState → GamepadState） │
│   UDP / TCP / BluetoothHID   │   BT/HID     │ ⑦ 后端 IVirtualControllerBackend │
└──────────────────────────────┘              │   ViGEmBus ｜ VIIPER            │
         ▲                                    └─────────────────────────────────┘
         └──── 震动 / 延迟 / 连接状态（反向通道）────┘
```

**这个项目真正的核心是 ①**——一份**设备无关的 `InputState`**，两端各自实现，协议是它的线格式。建议第一步就把它写成两份等价的结构体（C# record + Kotlin data class）+ 一份共享的测试向量文件（`protocol/testvectors/*.json`），两端各自跑通编解码再谈别的。

延迟链路各环节预算：

| 环节 | 典型值 | 可控性 |
|---|---|---|
| 触摸采样 + 屏幕刷新 | 8–16ms | 移动端工程（可优化到 120Hz） |
| 打包/发送 | <1ms | 自己写 |
| 网络 WiFi / ADB / BT | 2–8 / 3–10 / 10–30ms | 环境决定 |
| PC 解析 + 映射 | <1ms | 自己写 |
| 驱动提交 → 游戏轮询（60fps） | 0–17ms | **不可控**（游戏的轮询周期） |

结论：**别过度优化传输层**，端到端里最大的抖动来自游戏自身的输入轮询和无线环境。优先做对的是移动端采样节拍与 fail-safe。

## §6 协议草案 v1

### 6.0 通道划分

- **发现**：UDP 广播 `PADLINK_DISCOVER/1` → PC 单播回复 `{name, ip, port, ver, need_token}`
- **控制通道**：TCP（握手、配对/认证、创建/销毁虚拟手柄、能力协商、震动开关）
- **数据通道**：UDP（输入快照）+ 反向 UDP（震动）——或直接复用 control TCP 的写方向，二选一，⭐ D6
- BT HID 模式下降级为无控制通道（本地自持状态）

### 6.1 输入快照（JSON 形式，便于调试）

```json
{
  "v": 1,
  "seq": 12345,
  "ts": 1699999999123,
  "player": 0,
  "controller": "xbox360",
  "axes": { "lx": 0.5, "ly": -0.3, "rx": 0.0, "ry": 0.0, "lt": 0.8, "rt": 0.0 },
  "buttons": 5,
  "dpad": 2
}
```

相对企划的改动：
- 加 `seq`（统计丢包率必需）、`ts`（测延迟）、`v`（协议版本，为将来演进）。
- `buttons` 从 `{"a":true,"b":false,...}` 改为**位掩码整数**：省字节、比较快、JSON 与二进制形式可以共用同一套语义。
- `dpad` 用枚举（0=中立，1=上…8=右上），9 个方向比 4 个布尔更贴合真实手柄十字键。

### 6.2 输入快照（二进制形式，UDP 实测用）

固定 24 字节小端、无解析开销：

| offset | size | 字段 |
|---|---|---|
| 0 | 2 | magic `0x50 0x4C` |
| 2 | 1 | ver |
| 3 | 1 | player(2b) + controller(3b) + flags(3b) |
| 4 | 4 | seq (uint32) |
| 8 | 4 | ts (uint32，相对会话起点 ms) |
| 12 | 2 | buttons (bitmask) |
| 14 | 1 | dpad 枚举 |
| 15 | 1 | 保留/对齐 |
| 16 | 8 | 6 × int16：lx, ly, rx, ry, lt, rt（-32768..32767 映射 -1..1 或 0..1） |

### 6.3 时序约束（必须写进实现）

- **固定节拍发送**：60Hz（16.6ms）或 120Hz，由能力协商决定；**触摸事件不直接触发发包**。
- **全量快照**：每包都是完整状态，不做增量 → 丢包无害，这是 UDP 可用的前提。
- **保活**：输入无变化时降到 10Hz 仍继续发。
- **fail-safe**：PC 端 **300ms** 未收到数据帧 → 立即归零所有轴、松开所有键；恢复时从当前帧重建。移动端同理（断连时本地按键状态复位）。
- **TCP（ADB 模式）**：必须 `TCP_NODELAY` + 固定节拍发送。TCP 天然不丢包，但仍要保活和 fail-safe。

### 6.4 反向通道（震动）

```json
{ "v": 1, "type": "rumble", "left": 0.7, "right": 0.3 }
```
PC 端 `Submit` 后从驱动的震动回调里取强度，回推给对应 player。不做重传，丢一帧无所谓（下一帧会覆盖）。

## §7 安全

局域网内**任何设备**都能连上 PC 服务并注入输入。最低要求：

1. 首次连接需配对：PC 显示 6 位码，手机输入（或反之），换出长期 token 存本地。
2. 握手后所有控制帧带 token；数据帧带 session id。
3. 只监听 `0.0.0.0` 时给出明确风险提示，允许用户绑定到指定网卡。
4. 拒绝来自非配对设备的虚拟手柄创建请求（防止他人凭空给你开一个手柄）。

## §8 工程约定（建议直接采纳）

- 仓库分 `src/pc`（C#，`PadLink.sln`）、`src/android`（Kotlin，Gradle 工程）、`protocol/`（协议文档 + 测试向量，两端共同依赖的契约）。
- 协议改动必须同时更新 `protocol/` 与两端的编解码测试。
- 移动端先做**性能基准**（`MotionEvent` → 屏幕像素的端到端延迟、稳定 120Hz 输出），再堆功能。
